# 바이브 코딩 실습 노트 ① 명세 · 문서 체계

## ◈ 실습과제 목표 : TODO 앱을 개발 한다.
- 바이브코딩에 대한 개념을 세우는것이 목표
- AI와 협업하여, 요건정의 부터 배포까지 전 과정을 수행하는 능력을 기른다.
- TDD 기반 안정적인 코드 작성 습관
- 실무에 바로 적용 가능한 풀스택 개발 경험
- 업무를 쪼개서 기능 단위로 명세를 만들고, 전체적인 명세화 과정을 통해 AI 도구와 함께 프로젝트를 완성하고 검증하는 능력
- 작은 단위 컴포넌트 구성과 기능 확장에 대한 프론트 엔드 구축능력
- 에이전트 기반 개발 프로세스에서 개발자의 역할과 표준화된 형태의 팀 업무 프로세스를 수립하는 능력
- 요건 문서 작성 with LLM, 정의한 내용들을 실제 프로젝트 문서체계로 구체화
- LLM과 대화하면서 프로젝트 구조를 잡고 → 오류사항 점검 → 개발문서 정의 → TDD 방식 개발흐름 만들어 본다
- Specify를 이용한 SDD로 넘어간다(?)

## ◈ Vibecoding 요건문서 준비

### (1) PRD
- 제품 요구사항 - 무엇을 만드는가 (비즈니스 관점, 어떤 문제를 푸는가, 구체적인 기술 or 숫자는 없음)
- 사용자 시나리오나 어떤 범위가 포함되어야 하는지 명확히 해야 한다.
- 구체적인 요건들을 단계적으로 서술 해야한다.
- 무엇을, 기능목록, 사용자 시나리오

> **※ 효과적인 프롬프트**

```text
Tika 프로젝트의 PRD를 작성해줘. 다음 정보를 포함해야 해:

1. 제품 개요: 티켓 기반 칸반 보드 TODO 앱
2. MVP 범위: 단일 사용자, 고정 4컬럼(Backlog/TODO/In Progress/Done),
   티켓 CRUD, 드래그 앤 드롭, 계획시작일, 시작일, 계획종료일, 종료일
3. 2차 제외 범위: 인증, 커스텀 컬럼, 멀티사용자, 라벨/코멘트,
   파일 업로드는 2차 스펙이므로 제외할 것
4. 사용자 시나리오: 할 일 등록 → 상태 이동 → 수정/삭제 → 완료 확인
5. 핵심 기능 목록: REQUIREMENTS.md의 FR-001~008과 대응하는 기능 설명
6. 기술 스택 요약표: 선정 이유 포함(CLAUDE.md 참고)
7. 와이어프레임 참고: 좌측 Backlog 사이드바 + 우측 3컬럼 보드 Swimlane 레이아웃

CLAUDE.md를 읽고 이 정보를 바탕으로 PRD.md를 작성해줘.
형식은 마크다운으로 /docs/PRD.md에 저장해.
```

### (2) REQUIREMENTS - *Draft*
- 상세 요구사항
- US + FR + NFR 을 하나의 문서로 통합한것 (정확히 무엇을 만들지, 테스트 가능한 형태로 쪼갠 것)

#### 사용자 스토리
- 요구사항을 사용자의 관점에서 서술하는 기법 : 사용자가 왜 그 기능을 필요로 하는가를 드러낸다.
- 왜 추가해야 하는지를 알면, 우선순위 판단기준이 된다 + 적절한 UI와 흐름 설계
- 사용자 스토리 ↔ 기능 요구사항 ↔ 테스트 케이스 매핑 : 서로의 관계
- AI와 협업 활용 : 컨텍스트 전달에 유용함
- ex. 새 할일 등록 ↔ FR-001 ↔ TC-API-001.... 테스트 케이스들..
- 개발자와 AI가 구현할때 참조 + 왜 이 기능이 이런 형태여야 하는지 설명

#### FR / NFR
- FR (Functional Requirements) : 시스템이 무엇을 해야 하는가를 정의
- NFR (Non-Functional Requirements) : 시스템의 품질 속성 정의 (어떻게 수행해야 하는지) - 기술부채, 성능, 보안 등
- 기능요구사항 / 비기능 요구사항 ... 추적 매트릭스

> **※ 요구사항 작성예시**

````markdown
## Requirements
### User Stories
- 팀원으로서, 나는...

### Functional Requirements
- FR-1: 드래그앤드롭 시 status 필드 업데이트
- FR-2: ...

### Non-Functional Requirements
- NFR-1: 응답속도 200ms 이내
````

### (3) TRD
- 기술 요구사항 - 어떻게 만드는가 (어떤 기술/구조로 풀 것인지, 시스템 수준의 결정)
- 시스템 아키텍처, 디렉터리 구조, 데이터 흐름에 따른 구조적 일치를 검토
- 성능기준, 보안 등을 담는다.
- 어떻게, 기술적 결정을 명확히 전달
- 빠르게 MVP를 출시하고, 에이전트로 오류를 빠르게 디버깅 하는것
- 최신보다는 다음 기준으로 기술을 선정해야함 : AI 친화성 / 타입안정성 / 배포용이성
- 프론트엔드 : React + TypeScript
- 백엔드 : Node.js + Next.js API Routes (Vercel Serverless Functions)
- 데이터 베이스 : Vercel Postgres (Neon 기반, 서버리스 커넥션 풀 자동 관리)
- 호스팅 옵션 : Vercel (main 브랜치 push 시 자동 배포)

> **※ 효과적인 프롬프트**

```text
Tika 프로젝트의 TRD를 작성해줘. CLAUDE.md를 참고하고 다음 정보를 포함해야 해:

1. 시스템 아키텍처
   - 전체 구조: Vercel 단일 배포 (Next.js App Router + API Routes + Vercel Postgres)
   - 아키텍처 다이어그램: 프런트엔드 → Route Handler → Service → Drizzle → DB 흐름
   - 디렉터리 구조: app/api/(진입점), src/server/(백엔드 로직),
     src/client/(프런트 로직), src/shared/(공유 타입)

2. 기술 스택 상세
   - 각 기술의 버전, 선정 이유, 대안 비교 (예: Drizzle vs Prisma)
   - 프레임워크: Next.js 15 (App Router)
   - 런타임: Node.js (Vercel Serverless Functions)
   - ORM: Drizzle ORM (Vercel Postgres 공식 지원, 코드 생성 불필요)
   - DB: Vercel Postgres (Neon 기반, 서버리스 커넥션 풀 자동 관리)

3. 데이터 흐름
   - 읽기 흐름: 컴포넌트 → ticketApi.ts → /api/tickets → ticketService → DB
   - 쓰기 흐름: 폼 → Zod 검증 → ticketApi.ts → /api/tickets → ticketService → DB
   - 드래그 앤 드롭: 낙관적 업데이트 → PATCH /api/tickets/:id → position 재계산

4. 계층 간 경계 규칙
   - src/server/ ↮ src/client/ 상호 import 금지
   - src/shared/만 양쪽에서 참조 가능
   - Route Handler는 얇게 유지: 요청 파싱 → 서비스 호출 → 응답 반환

5. 개발 환경 설정
   - 로컬 DB: vercel env pull로 환경 변수 가져오기
   - 테스트: Jest + React Testing Library
   - Lint: ESLint + Prettier

6. 배포 전략
   - Vercel 자동 배포 (main 브랜치 push)
   - Preview 배포 (PR 생성 시)
   - 환경 변수: Vercel Dashboard에서 관리

형식은 마크다운으로, /docs/TRD.md에 저장해줘.
PRD.md의 기능 목록 및 기술 스택 요약표와 일치하는지 확인해줘.
```

### (6) API 설계
- 프론트엔드 (= 컴포넌트 - 로직 - API클라이언트함수) <-----> 백엔드 엔드포인트
- 프론트 엔드와 백엔드 사이의 계약
- DATA_MODEL.md (이미 완성됨 - tickets 테이블, 컬럼, 비즈니스 규칙) → 이 데이터를 "어떻게 조작할지"가 곧 API
- 이번 과제에서는 티켓 CRUD와 상태/순서 변경등 총 8개의 엔드포인트로 구성
- 코드별 에러메시지, 공통코드 규칙 정의 필요

> **※ API 설계 실전 작성 순서**

| 단계 | 할 일 | 설명 |
| --- | --- | --- |
| 1단계 | FR 목록 훑어보기 | 필요한 기능들을 동작 단위로 나열한다. (예: "티켓 생성", "상태 변경" 등) |
| 2단계 | 각 기능을 CRUD 동사로 매핑 | "생성/조회/수정/삭제" 중 어디에 해당하는지 분류한다. |
| 3단계 | CRUD를 HTTP Method + URL로 변환 | Create→POST, Read→GET, Update→PATCH, Delete→DELETE 공식대로 URL을 붙인다. (예: `POST /api/tickets`) |
| 4단계 | DATA_MODEL 컬럼표를 보고 요청 값 정의 | 사용자가 직접 입력해야 하는 컬럼(NOT NULL이면서 자동생성이 아닌 것)만 요청 Body에 넣는다. |
| 5단계 | DATA_MODEL 컬럼표를 보고 응답 값 정의 | id, status, position, createdAt 등 자동 생성/계산되는 컬럼까지 포함해 전체 컬럼을 응답 Body에 넣는다. |
| 6단계 | 비즈니스 규칙을 응답에 반영 | completedAt처럼 특정 조건에서 자동으로 채워지는 값을 응답 예시에 명시한다. |
| 7단계 | 스펙 옆에 실제 값 예시 추가 | 타입 설명만 있는 스펙 아래에, 진짜 값이 채워진 요청/응답 JSON 예시를 같이 적는다. |

> **※ 선행 문서의 품질이 곧 API 품질**

"FR 문서를 살펴보고 DATA_MODEL.md를 참고해서 URL과 HTTP API 스펙을 그대로 작성해달라고 요청"

이 말은 **AI가 API_SPEC을 잘 만들려면, 그 전 단계(FR, DATA_MODEL)가 이미 정확하고 구체적으로 준비되어 있어야 한다**는 뜻이다.

```text
FR이 애매하면                          → API도 애매하게 나옴
DATA_MODEL에 비즈니스 규칙이 빠져있으면 → completedAt 같은 필드가 응답에서 누락됨
```

> **※ 개발자 역할의 변화**

"개발자는 스펙에 대한 필드가 제대로 되었는지 검증만 해보면 된다"

- 예전: 개발자가 **작성자**
- 지금: 개발자가 **검토자/설계자**

AI가 만든 API_SPEC이 정말 DATA_MODEL의 컬럼과 다 맞는지, 비즈니스 규칙이 응답에 잘 반영됐는지 **확인하는 눈**은 여전히 사람 몫이다. 요청/응답 구분, 기본값 채우기 원리, 비즈니스 규칙 반영 방식을 이해하고 있는 것이 곧 **그 검증을 제대로 할 수 있는 능력**이 된다.

### (7) 컴포넌트 및 UseCase 설계
- 컴포넌트의 책임, 입력/출력, 상태를 정의 한다.
- 컴포넌트는 시각적 조각 + 코드단위(로직)
- AI에게 작업요청시, 이 명세들을 바탕으로 Props, 상태관리, 컴포넌트 구조를 작성하므로 스펙 정의 필요
- 상세 내용은 검토를 하면서 수정해나가야 한다.
- 컴포넌트 계층, Props, 이벤트 흐름
- User Story와 컴포넌트 매핑

> **※ 컴포넌트 / State / Props**

```text
서버 (DB)
  ↓ API 호출
부모 컴포넌트 (TicketBoard)
  - 서버에서 티켓 "목록 전체"를 한 번에 받아옴
  - 이 전체 목록을 State로 가지고 있음
  ↓ 하나씩 쪼개서 Props로 전달
자식 컴포넌트 (TicketCard) × 여러 개
  - 각자 "자기 것 하나"만 Props로 받아서 화면에 그림
```

| 구분 | 컴포넌트 | 가진 것 | 역할 |
| --- | --- | --- | --- |
| 부모 | TicketBoard | State (티켓 목록 전체) | API로 목록 전체를 받아 보관하고, 하나씩 쪼개서 내려보냄 |
| 자식 | TicketCard × N | Props (티켓 1개) | 받은 티켓 하나만 화면에 그림 |

- **State** = 그 컴포넌트가 직접 소유하고 바꿀 수 있는 데이터 (부모에 둔다)
- **Props** = 부모가 자식에게 내려주는 읽기 전용 데이터

### (8) Test 케이스 정의

- 추적 매트릭스와의 연결 : 요구사항과 테스트 케이스가 빠짐없이 연결되어 있는지 확인하는 표

```text
TEST_CASES.md

```

| 분류 | 테스트 ID | 개수 | 담당 |

## ◈ 명세 작업의 기본
- 철저하게 작성된 FR, NFR, US 와 같은 요구사항 정의
- 잘 모델링된 DB
- 개발 프로젝트의 전체 흐름과 기능정의다
- 지금까지 설계한 API, 컴포넌트, 데이터모델, 테스트 케이스는 각각 서로 참조, 의존하는관계

> FR, NFR, User Story, DATA_MODEL 같은 모든 것의 뿌리가 되는 문서는 AI가 초안을 만들어주더라도,
> 사람이 서로 앞뒤가 맞는지 꼼꼼히 대조/확인하고 확정해야 한다.
> 그렇게 탄탄하게 확정된 근거 문서가 있어야 API_SPEC이나 COMPONENT_SPEC 같은 나머지 문서들을
> AI에게 상대적으로 안심하고 맡길 수 있다.

> "명세 작업"의 범위는 FR/NFR/User Story(요구사항) → TRD → DATA_MODEL → API_SPEC → COMPONENT_SPEC → TEST_CASES까지 전부를 포함한다.
> PRD는 그 앞 단계인 "기획"에 더 가깝다.
> 이 문서들은 위에서 정리한 것처럼 서로 참조하고 의존하기 때문에, 어느 한 문서(특히 근거가 되는 FR/DATA_MODEL)가
> 부실하면 뒤따르는 모든 명세 문서가 줄줄이 영향을 받는다는 것이 핵심이다.


## ◈ SDD 워크플로
- Spec Kit 명령어를 활용해서 명세확인 → 계획수립 → 작업분해 → 구현실행 사이클을 반복한다.
- 작은 단위의 커밋을 실행하여, 깃에 Push
- 새 디렉터리를 생상허며 초기화 하는 경우 : specify init my-project --ai claude
- 위 명령어는 바뀜
- specify init --here --integration claude
