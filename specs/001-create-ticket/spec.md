## User Scenarios & Testing *(mandatory)*

### User Story 1 - 제목만으로 할 일 빠르게 등록 (Priority: P1)

사용자는 떠오른 할 일을 제목만 입력해서 즉시 등록한다. 등록된 할 일은 Backlog 칼럼의 맨 위에
나타나고, 우선순위는 따로 고르지 않아도 "보통(MEDIUM)"으로 정해진다.

**Why this priority**: 할 일을 기록하는 것이 이 앱의 출발점이다. 이것 없이는 보드에 보여줄 것도,
옮길 것도 없다. 이 스토리 하나만으로도 "잊지 않게 적어 두기"라는 핵심 가치를 준다.

**Independent Test**: 제목만 넣어 티켓을 하나 만들고, 돌려받은 티켓 정보에서 상태·우선순위·위치·
비어 있어야 할 필드를 확인하면 단독으로 검증된다.

**Acceptance Scenarios**:

1. **Given** 보드가 있는 상태에서, **When** 제목 "테스트 할일"만 입력해 생성하면, **Then** 티켓이
   생성되고 상태는 Backlog, 우선순위는 MEDIUM, 설명·시작예정일·종료예정일은 비어 있다. (TC 001-1)
2. **Given** 새로 생성된 티켓에 대해, **When** 생성 결과를 확인하면, **Then** 시작일과 종료일은
   비어 있다. (TC 001-11)
3. **Given** Backlog에 티켓이 이미 있는 상태에서, **When** 새 티켓을 연속으로 2개 만들면, **Then**
   나중에 만든 티켓이 Backlog의 가장 위에 놓인다. (TC 001-10)
4. **Given** Backlog가 비어 있는 상태에서, **When** 티켓을 하나 만들면, **Then** 그 티켓이 Backlog의
   유일한 티켓으로 놓이고 순서값은 −1024다.
5. **Given** 정상 입력으로, **When** 생성이 성공하면, **Then** 생성된 티켓의 전체 정보(식별자, 입력값,
   상태, 순서, 시작일·종료일, 생성·수정 시각)를 돌려받는다.

### User Story 2 - 잘못된 입력은 거부하고 이유를 알려줌 (Priority: P2)

사용자가 규칙에 맞지 않는 값을 넣으면 티켓은 만들어지지 않고, 무엇이 잘못됐는지 한국어 메시지로
안내받는다.

**Why this priority**: 잘못된 데이터가 보드에 쌓이는 것을 막고, 사용자가 바로 고쳐서 다시 시도할 수
있게 한다. 등록 자체(P1)가 있어야 의미가 있으므로 그다음 순위다.

**Independent Test**: 각 잘못된 입력 유형을 하나씩 보내고, 생성이 거부되는지와 메시지가 문서와
정확히 같은지 확인한다.

**Acceptance Scenarios**:

1. **Given** 제목 없이, **When** 생성하면, **Then** 거부되고 "제목을 입력해주세요"가 안내된다. (TC 001-3)
2. **Given** 빈 문자열 제목으로, **When** 생성하면, **Then** 거부되고 "제목을 입력해주세요"가 안내된다. (TC 001-4)
3. **Given** 공백만 있는 제목("   ")으로, **When** 생성하면, **Then** 거부되고 "제목을 입력해주세요"가 안내된다. (TC 001-5)
4. **Given** 201자 제목으로, **When** 생성하면, **Then** 거부되고 "제목은 200자 이내로 입력해주세요"가 안내된다. (TC 001-6)
5. **Given** 1001자 설명으로, **When** 생성하면, **Then** 거부되고 "설명은 1000자 이내로 입력해주세요"가 안내된다. (TC 001-7)
6. **Given** 우선순위 "URGENT"로, **When** 생성하면, **Then** 거부되고 "우선순위는 LOW, MEDIUM, HIGH 중 선택해주세요"가 안내된다. (TC 001-8)
7. **Given** 종료예정일 2020-01-01로, **When** 생성하면, **Then** 거부되고 "종료예정일은 오늘 이후 날짜를 선택해주세요"가 안내된다. (TC 001-9)
8. **Given** 시작예정일 "2026-13-45"로, **When** 생성하면, **Then** 거부되고 "시작예정일 형식이 올바르지 않습니다"가 안내된다.
9. **Given** 종료예정일 "내일"로, **When** 생성하면, **Then** 거부되고 "종료예정일 형식이 올바르지 않습니다"가 안내된다.
10. **Given** 위 어떤 경우든, **When** 거부되면, **Then** 티켓은 하나도 저장되지 않는다.

### User Story 3 - 등록하면서 상세 정보까지 설정 (Priority: P3)

사용자는 등록할 때 설명, 우선순위, 시작예정일, 종료예정일을 함께 입력해서 할 일의 중요도와 기한을
처음부터 정해 둔다.

**Why this priority**: 중요도와 기한 관리는 가치가 크지만, 제목만으로 등록(P1)한 뒤 나중에 수정할
수도 있으므로 P3이다.

**Independent Test**: 모든 선택 필드를 채워 티켓을 만들고 돌려받은 정보에 각 값이 그대로 반영됐는지
확인한다.

**Acceptance Scenarios**:

1. **Given** 제목·설명·우선순위 HIGH·시작예정일·종료예정일을 모두 입력해, **When** 생성하면,
   **Then** 모든 값이 그대로 반영된 티켓이 만들어진다. (TC 001-2)
2. **Given** 종료예정일을 오늘 날짜로, **When** 생성하면, **Then** 정상 생성된다.
3. **Given** 시작예정일을 과거 날짜로, **When** 생성하면, **Then** 정상 생성된다(시작예정일에는 날짜
   범위 제한이 없다).
4. **Given** 시작예정일이 종료예정일보다 늦게, **When** 생성하면, **Then** 정상 생성된다.

---

### Edge Cases

- 제목이 정확히 200자이면 허용되고, 201자부터 거부된다.
- 설명이 정확히 1000자이면 허용되고, 1001자부터 거부된다.
- 제목 앞뒤에 공백이 있지만 내용이 있는 경우(예: "  할 일  ")는 허용되며 입력한 그대로 저장된다.
- "오늘" 판정은 한국 시간(Asia/Seoul) 기준이다. 예: 한국 시간 2026-03-11 00:30(국제 표준시로는
  2026-03-10 15:30)에는 "오늘"이 2026-03-11이므로, 종료예정일 2026-03-10은 거부되고 2026-03-11은 허용된다.
- 사용자가 상태, 순서, 시작일, 종료일 등 시스템이 관리하는 값을 함께 보내더라도 반영되지 않는다.
  새 티켓은 항상 Backlog에서 시작하고 시작일·종료일은 비어 있다.
- 여러 필드가 동시에 잘못된 경우에도 거부되며, 안내 메시지는 하나만 표시된다.
- 날짜 필드가 연-월-일 형식이 아니거나 존재하지 않는 날짜(예: "2026-13-45", "내일")인 경우는
  거부된다. 이때 안내 메시지는 FR-013을 따른다.
- 시작예정일이 종료예정일보다 늦은 경우(예: 시작 3/20, 종료 3/10)도 정상 생성된다. (FR-014)
- 저장 중 시스템 오류가 나면 티켓은 생성되지 않고, 내부 오류 세부 정보(시스템 메시지, 저장소 오류
  등)는 사용자에게 노출되지 않는다.

## Requirements *(mandatory)*

> 아래 FR 번호는 이 spec 안에서만 쓰는 번호다. 기준 문서와의 대응은 각 항목의 괄호에 표기한다.

### Functional Requirements

- **FR-001**: 시스템은 사용자가 제목(필수)과 설명·우선순위·시작예정일·종료예정일(선택)을 입력해
  새 티켓을 만들 수 있게 해야 한다. (docs FR-001, US-001, US-002)
- **FR-002**: 제목은 반드시 있어야 하며 1~200자여야 하고, 공백만으로 이뤄질 수 없다.
- **FR-003**: 설명은 최대 1000자이며, 입력하지 않으면 비어 있는 상태로 저장된다.
- **FR-004**: 우선순위는 LOW, MEDIUM, HIGH 중 하나여야 하며, 입력하지 않으면 MEDIUM이 적용된다.
- **FR-005**: 시작예정일과 종료예정일은 선택 입력이며 연-월-일 날짜다. 입력하지 않으면 비어 있다.
- **FR-006**: 종료예정일은 오늘 또는 그 이후 날짜만 허용한다. "오늘"은 서버·사용자 환경의 시간대와
  관계없이 항상 한국 시간(Asia/Seoul)의 날짜로 판정한다. (사용자 결정 2026-10-10)
- **FR-007**: 새 티켓의 상태는 입력과 관계없이 항상 Backlog다.
- **FR-008**: 새 티켓은 Backlog 칼럼의 기존 모든 티켓보다 위(맨 위)에 놓인다. 칼럼 내 순서값은
  "Backlog의 가장 작은 순서값 − 1024"이며, Backlog가 비어 있으면 0을 기준으로 삼아 첫 티켓의
  순서값은 −1024가 된다. (사용자 결정 2026-10-10, `docs/API_SPEC.md` §1 기준)
- **FR-009**: 새 티켓의 시작일과 종료일은 비어 있으며, 사용자가 생성 시 지정할 수 없다.
  (시작일·종료일은 상태 이동의 결과로만 기록된다.)
- **FR-010**: 시스템은 티켓의 생성 시각과 수정 시각을 자동으로 기록한다.
- **FR-011**: 생성에 성공하면 생성된 티켓의 전체 정보를 돌려준다.
- **FR-012**: 입력이 규칙에 맞지 않으면 티켓을 만들지 않고, "검증 오류"임을 나타내는 오류 코드와
  아래 메시지를 문구 그대로 돌려준다.

  | 조건 | 메시지 |
  |------|--------|
  | 제목 누락 / 빈 제목 / 공백만 입력 | "제목을 입력해주세요" |
  | 제목 200자 초과 | "제목은 200자 이내로 입력해주세요" |
  | 설명 1000자 초과 | "설명은 1000자 이내로 입력해주세요" |
  | 허용되지 않는 우선순위 | "우선순위는 LOW, MEDIUM, HIGH 중 선택해주세요" |
  | 과거 종료예정일 | "종료예정일은 오늘 이후 날짜를 선택해주세요" |

- **FR-013**: 시작예정일 또는 종료예정일이 올바른 연-월-일 날짜가 아니면 티켓을 만들지 않고, 필드별로
  아래 메시지를 검증 오류로 돌려준다. (docs 반영 필요 — 현재 기준 문서에 없는 문구)

  | 조건 | 메시지 |
  |------|--------|
  | 시작예정일 형식 오류 | "시작예정일 형식이 올바르지 않습니다" |
  | 종료예정일 형식 오류 | "종료예정일 형식이 올바르지 않습니다" |

- **FR-014**: 시작예정일이 종료예정일보다 늦은 입력도 허용한다. 두 날짜 사이의 순서는 검사하지 않는다.
- **FR-015**: 모든 오류 안내는 "오류 코드 + 사람이 읽는 메시지"의 같은 형태로 전달되며, 내부 시스템
  정보를 포함하지 않는다.
- **FR-016**: 입력 화면에서 하는 검증과 서버에서 하는 검증은 같은 규칙과 같은 메시지를 쓴다.
  (docs NFR-004)

### Key Entities *(include if feature involves data)*

- **티켓(Ticket)**: 사용자가 관리하는 할 일 하나.
  - 사용자가 입력하는 값: 제목, 설명, 우선순위, 시작예정일, 종료예정일
  - 시스템이 정하는 값: 식별자, 상태(생성 시 Backlog), 칼럼 내 순서, 시작일·종료일(생성 시 비어 있음),
    생성 시각, 수정 시각

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 제목 한 가지만 입력해서 할 일 하나를 등록할 수 있다(필수 입력 1개).
- **SC-002**: 티켓 생성 요청의 95%가 0.3초 이내에 결과(성공 또는 거부 안내)를 돌려준다. (docs NFR-001)
- **SC-003**: `docs/TEST_CASES.md` TC-API-001의 11개 시나리오와 날짜 형식 오류 시나리오 2개(FR-013)가
  모두(100%) 기대 결과대로 동작한다.
- **SC-004**: 규칙에 맞지 않는 입력으로 저장된 티켓이 0건이며, 거부 시 안내 메시지가 기준 문서
  문구와 100% 일치한다.
- **SC-005**: 티켓을 연속으로 여러 개 만들 때, 가장 마지막에 만든 티켓이 항상(100%) Backlog 맨 위에
  나타난다.

## Assumptions

- 단일 사용자 앱이며 인증이 없으므로, 생성 권한 확인은 범위 밖이다. (docs PRD)
- "오늘 이후"는 오늘을 포함한다. 이는 기준 문서의 검증 규칙(오늘 날짜와 같거나 이후)에 따른 해석이다.
- 시작예정일에는 날짜 범위 제한이 없다(과거·미래 모두 허용). 기준 문서에 제한이 없기 때문이다.
- 이 spec의 결정 중 기준 문서와 아직 맞지 않는 부분은 plan/tasks 단계의 작업으로 처리한다
  (docs 수정을 코드 수정보다 먼저 한다):
  - FR-013 날짜 형식 오류 메시지 2개 → `docs/REQUIREMENTS.md`·`API_SPEC.md`·`TEST_CASES.md`에 추가
  - FR-008 빈 칼럼 첫 티켓 순서값 −1024 → `docs/REQUIREMENTS.md` 28행 수정
  - FR-006 "오늘" Asia/Seoul 판정 → `docs/API_SPEC.md` 생성 스키마 예시 수정
  - 현재 구현은 FR-008(빈 칼럼에 0 사용)과 FR-006(국제 표준시로 오늘 계산)을 따르지 않으므로 수정 대상이다.

  않는다. 오류 응답 형식이 메시지 하나만 담기 때문이다.

- 생성 폼 화면(버튼, 모달 열기/닫기)은 이 spec의 범위 밖이며, 보드 화면 기능에서 다룬다.
  이 spec은 "티켓을 만든다"는 동작과 그 규칙만 다룬다.
- 기준 문서(`docs/`)가 이 spec보다 우선한다. 충돌이 발견되면 docs를 먼저 고친 뒤 이 spec에 반영한다.
